  - `[Cliente Web Flutter SPA / CanvasKit]` ➔ HTTPS ➔ `[Kong API Gateway]` ➔ `[Supabase Edge Functions en Deno Runtime]` ➔ `[PostgreSQL 17 ACID + RLS]` + `[Groq API Cloud]`
- **Bullets en Pantalla (Máximo 3):**
  - Frontend SPA en Flutter Web desacoplado de la persistencia directa.
  - Backend Serverless sobre Deno Runtime: arranque en frío <50 ms.
  - Persistencia relacional en PostgreSQL 17 con Row Level Security (RLS).

#### B. Notas Privadas del Orador (Discurso Verbal - Solo en Portátil)
> "Nuestra arquitectura fue diseñada bajo el Modelo C4. En el nivel de contenedores, aplicamos una separación radical de responsabilidades: el cliente es una aplicación web en Flutter que renderiza en CanvasKit para brindar animaciones fluidas a 60 cuadros por segundo sin sobrecargar el DOM.  
> La aplicación jamás se conecta directamente a la base de datos ni a los proveedores de inteligencia artificial. Todas las comunicaciones transitan por un API Gateway Kong hacia diez Supabase Edge Functions ejecutadas en el runtime Deno. ¿Por qué Deno y no Node.js tradicional? Porque Deno se ejecuta en el borde geográfico más cercano al usuario, tiene un tiempo de arranque casi nulo y opera bajo un modelo de seguridad por permisos estrictos. En la base de datos, PostgreSQL 17 orquesta procedimientos transaccionales RPC que aseguran la consistencia ACID de cada partida."  
*Transición:* "¿Cómo aseguramos la mantenibilidad de este código? Mediante principios SOLID y la filosofía de los 12 Factores."

#### A. Contenido Visual de la Lámina (Pantalla de Proyección)

- **Composición Visual:** Tabla de doble entrada con evidencias concretas del repositorio:
  - *Principio SOLID:* Inversión de Dependencias (DIP) ➔ `CombateController` desacoplado mediante interfaz abstracta `QuestRepository`.
  - *Principio SOLID:* Responsabilidad Única (SRP) ➔ Validadores de esquema aislados de la lógica de red.
  - *12 Factores (Factor III, VI, IX):* Configuración estricta en `.env`, procesos stateless en el borde y desechabilidad inmediata.
- **Bullets en Pantalla (Máximo 3):**
  - Clean Architecture en Flutter: separación estricta de Domain, Infra y Presentation.
  - Procesos Serverless sin estado: escalabilidad horizontal automática.
  - Flujo GitFlow con Conventional Commits y Pull Requests obligatorios.

#### B. Notas Privadas del Orador (Discurso Verbal - Solo en Portátil)
> "No seleccionamos tecnologías por moda ni por conveniencia momentánea, sino por justificación técnica. En el frontend aplicamos Inversión de Dependencias: nuestros controladores no conocen la librería HTTP concreta; dependen de contratos e interfaces puras. Esto nos permitió, por ejemplo, probar toda la lógica de combate con stubs simulados antes de tener el backend desplegado.  
> En el backend adoptamos la metodología de las aplicaciones de Doce Factores: factor tres, configuración estricta por entorno, donde ninguna clave privada ni token de servicio reside en el repositorio; factor seis, procesos sin estado, garantizando que si mil estudiantes entran simultáneamente, las funciones escalan de forma transparente; y factor nueve, desechabilidad con apagado limpio. Cada cambio fue gestionado en Git mediante Conventional Commits y revisiones de código cruzadas."  
*Transición:* "Una arquitectura sólida debe demostrar su calidad con pruebas irrefutables. Entremos a la etapa de Calidad y Verificación."
